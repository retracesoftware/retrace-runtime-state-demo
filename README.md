# Retrace Runtime-State Demo

This repository demonstrates the two ways Retrace investigates a Python
failure:

1. **Retrace AI debugger:** record a real pytest failure, replay it, inspect
   the preserved runtime state, and generate an evidence-backed bug report.
2. **Retrace VS Code debugger:** open that exact recording, stop at the
   historical failure path, and inspect its stack, scopes, and local variables.

The demo is self-contained. Docker supplies Python, pytest, Retrace, and a
small HTTP API. The default hosted AI allowance does not require a
`RETRACE_API_KEY`.

## The Runtime Bug

The application requests a newly generated order batch from an HTTP API. One
order is fully returned, so values that exist only in that live response
satisfy:

```text
retained_units = shipped_units - returned_units
retained_units = 16 - 16 = 0
```

The application calculates:

```python
net_revenue_cents / retained_units
```

and raises `ZeroDivisionError`.

Every run receives different batch, order, customer, quantity, and financial
values. Retrace preserves the original response in the recording. Replay and
debugging therefore reproduce the exact incident without contacting the API
again.

## Requirements

- Git
- Docker Desktop or Docker Engine with Docker Compose
- Internet access for hosted AI report generation
- VS Code for reading the report and visual replay debugging
- The VS Code Dev Containers extension for visual replay debugging

The demo runs on macOS and Linux hosts supported by Docker.

Start Docker and wait until it reports that the engine is running. Install the
Dev Containers extension with:

```bash
code --install-extension ms-vscode-remote.remote-containers
```

If `code` is not available in a macOS terminal, open VS Code, run
**Shell Command: Install 'code' command in PATH** from the Command Palette,
and then open a new terminal.

You do not need Python, Retrace, SQL Server, or an API key installed on the
host. Docker supplies the Python and Retrace environment, and the default
hosted AI allowance is requested automatically.

## Validation Modes And Model Usage

Routine development checks do not contact a language model:

```bash
make test
make debugger-verify-example
```

`make test` validates the structured-report renderer and report quality gate
using local fixtures. `make debugger-verify-example` uses the checked-in
recording to validate replay and DAP behavior. Both are repeatable and consume
no hosted-model quota.

`make run` is the intentional live demo described below. It records a fresh
incident and requests a hosted AI investigation. The normal interactive flow
may request one correction of the same recording if the first report fails the
quality gate.

The repeated live-model harness is not part of push or pull-request testing.
The old `make stress` shortcut is disabled to prevent accidental five-run
model use. Maintainers can explicitly request one bounded live run with:

```bash
RETRACE_API_KEY=... make live-ai-harness
```

Set `LIVE_AI_RUNS` to a value from 1 through 5 only when repeated live evidence
is genuinely required. The manually dispatched GitHub workflow always runs once,
requires the repository `RETRACE_API_KEY` secret, disables anonymous access,
and disables the automatic correction attempt.

## Part 1: Generate A Fresh Trace And AI Bug Report

Run:

```bash
make run
```

That is the complete quick start. It performs setup and then runs the demo.

### What `make run` does

`make run` first performs the `make setup` steps:

1. Verify that Docker and Docker Compose are available.
2. Pull the Python image used by the incident API.
3. Build the Python 3.12.13 Linux/amd64 demo image.
4. Install `retracesoftware==0.2.30` from PyPI. Its
   `retracesoftware-dap==0.2.30` dependency is installed automatically.
5. Start the incident API and wait for its health check.

It then:

1. Deletes artifacts generated by a previous live run.
2. Requests a fresh order batch from the API.
3. Runs the real pytest command through Retrace:

   ```bash
   RETRACE_AUTO_DEBUG=1 \
   retracepython --recording /app/recordings/runtime-incident.retrace \
     -m pytest -vs tests
   ```

4. Records the API response and expected pytest failure.
5. Replays the recording through DAP so the AI debugger can inspect stack,
   source, scopes, and historical local variables.
6. Writes the native AI output and a readable bug report.
7. Directly replays the recording one more time.
8. Verifies that recording and both replay paths made only one live API
   request in total.
9. Validates that the report contains the exact runtime identifiers,
   arithmetic, failure location, root cause, and a safe full-return handling
   recommendation.

If the model's first summary does not match the evidence it collected, the
interactive `make run` quality gate asks the AI debugger to reinvestigate the
same recording once.
This correction pass does not rerun pytest and does not contact the incident
API. Only an evidence-consistent report is presented as successful.

Set `RETRACE_AI_CORRECTION_ATTEMPTS=0` to fail immediately instead of making
that second model request. The manual harness uses this setting.

`make setup` may also be run separately when you want to prepare the images
and API before presenting:

```bash
make setup
```

### The pytest failure is expected

During `make run`, pytest intentionally prints output similar to:

```text
tests/test_order_metrics.py::test_unit_economics_report_contains_every_order FAILED
E   ZeroDivisionError: division by zero
Retrace auto-debug: target exited with code 1; running AI debugger for ...
```

Do not stop the command when `FAILED` or `ZeroDivisionError` appears. That is
the target application incident Retrace is recording. The next line means
Retrace has started reading and replaying the trace so the AI debugger can
investigate it.

The overall demo succeeds only after the expected target failure has been
replayed, diagnosed, reported, and validated.

Near the end of a successful run, look for:

```text
Report quality validation passed.
Replay reproduced the runtime failure without another API request.
Runtime-state demo succeeded.
Live API requests across record, AI replay, and direct replay: 1
```

The exact batch, order, customer, quantity, and financial values are expected
to change on each new live run.

### Generated artifacts

The current run produces:

```text
recordings/runtime-incident.retrace
reports/runtime-bug-report.md
reports/runtime-incident.ai-report.md
reports/runtime-incident.ai-report.json
reports/runtime-payload.json
reports/demo-terminal.log
reports/replay-terminal.log
```

The most useful file to read is:

```text
reports/runtime-bug-report.md
```

Confirm that the recording, readable report, and captured payload all exist
and are nonempty:

```bash
ls -lh recordings/runtime-incident.retrace
ls -lh reports/runtime-bug-report.md
ls -lh reports/runtime-payload.json
```

These files contain:

```text
recordings/runtime-incident.retrace
    The Retrace recording of the failed pytest execution.

reports/runtime-bug-report.md
    The readable AI-generated diagnosis.

reports/runtime-payload.json
    The original live API data used by this execution.
```

Open it with:

```bash
make report
```

or:

```bash
code reports/runtime-bug-report.md
```

The report is live, not a checked-in answer. Before every run, the script
removes the previous generated report and recording. The unique batch, order,
customer, and financial values in the report must match
`reports/runtime-payload.json` from that run.

The readable report includes a **Verified DAP Runtime State** section copied
verbatim from the historical `runtime_incident_evidence` local in the
preserved debugger transcript. The AI supplies the diagnosis and suggested
fix; the report keeps exact runtime identifiers and numbers anchored to the
debugger evidence even when prose summarization is shorter.

A successful report identifies:

- the exact runtime-created batch, order, and customer
- shipped and returned quantities
- `retained_units = 0`
- gross, refunded, and net revenue
- the failing test and production helper
- the division by zero root cause
- an explicit recommendation for fully returned orders, such as skipping an
  undefined per-retained-unit metric or representing it as not applicable
  before division

It should not silently recommend numeric zero unless the application owner has
defined that business meaning.

The readable report also separates the observed symptom, immediate mechanism,
triggering runtime input, application defect, evidence-backed causal chain,
and the runtime fact uniquely established by the recording. Any degraded
debugger capabilities or unresolved causal links are shown explicitly, along
with the focused regression condition that should accompany the fix.

To verify manually that the report describes this exact run, display the
captured payload and the report's verified debugger evidence:

```bash
cat reports/runtime-payload.json
grep -A4 "Verified DAP Runtime State" reports/runtime-bug-report.md
```

The batch ID, order ID, customer ID, and numeric values must match. This proves
that the report came from the fresh recording rather than a checked-in answer.

### Replay the trace again

Run:

```bash
make replay
```

Expected final output:

```text
Replay reproduced the runtime failure without another API request.
```

This proves that replay uses the recorded API response rather than fetching a
new batch.

## Part 2: Debug That Exact Run In VS Code

Complete Part 1 first. The VS Code workspace is configured to select the
fresh recording created by `make run`:

```text
/app/recordings/runtime-incident.retrace
```

Do not run `make clean` between Part 1 and Part 2 because it removes the live
recording.

### 1. Install the Dev Containers extension

```bash
code --install-extension ms-vscode-remote.remote-containers
```

### 2. Open the repository

From the repository root:

```bash
code .
```

### 3. Reopen it inside the demo container

In VS Code:

1. Open the Command Palette with `Cmd+Shift+P` on macOS or `Ctrl+Shift+P` on
   Linux.
2. Run **Dev Containers: Reopen in Container**.
3. Wait for the image and remote extensions to finish installing.
4. Confirm the lower-left corner says **Dev Container: Retrace VS Code Demo**.

The VS Code window remains on the host. The matching Python environment,
Retrace extension, replay process, and DAP adapter run inside the container.
The source repository is mounted at `/app`, exactly matching the path stored
in the recording.

### 4. Verify the fresh recording automatically

Open a terminal in the Dev Container and run:

```bash
python /app/scripts/verify_debugger.py \
  --recording /app/recordings/runtime-incident.retrace
```

Expected output ends with:

```text
demo=runtime-state-live direct_replay=pass breakpoint=pass stack=pass scopes=pass locals=pass exact_runtime_values=pass
```

This verifies that the VS Code/DAP environment can:

- replay the exact recording generated in Part 1
- reproduce its `ZeroDivisionError`
- find and stop at the source breakpoint
- read stack frames and scopes
- inspect the historical locals
- match those locals to the exact payload and bug report from Part 1

You can run the same check from the VS Code Command Palette with
**Tasks: Run Task**, then select **Retrace: verify fresh runtime recording**.

### 5. Set the breakpoint

Open:

```text
/app/tests/test_order_metrics.py
```

Set a breakpoint on line 31:

```python
revenue_per_retained_unit = calculate_revenue_per_retained_unit(
```

### 6. Start Retrace replay debugging

In VS Code:

1. Click the Retrace icon in the left activity bar.
2. Find the recorded Python process, shown as `python (PID ...)`.
3. Click play beside that process.
4. Wait for breakpoint scanning to complete.
5. Retrace first pauses at an entry stop. Press `F5` or **Continue** once. Do
   not use Step Into until the source breakpoint has been reached.
6. Replay stops at the breakpoint on line 31.

The Debug Console should show messages similar to:

```text
breakpoint scan[1]: complete, 2 hits found
handleContinue: cursor=false ...
handleContinue: ok=true hitMsgIdx=...
```

An initial `stackTrace: no active cursor` message means replay has not moved
from the entry stop to an inspectable historical position yet. If pressing
Continue produces no `handleContinue` message, stop the debug session with
`Shift+F5`, run **Developer: Reload Window**, start the recorded process again,
wait for breakpoint scanning to complete, and press `F5`. You can also run
**Debug: Continue** from the Command Palette.

### 7. Inspect the historical runtime state

Open **Run and Debug**, then expand **Variables** and **Locals**. Inspect:

```text
batch_id
order_id
customer_id
shipped_units
returned_units
retained_units
gross_revenue_cents
refunded_revenue_cents
net_revenue_cents
runtime_incident_evidence
```

These values must match the unique values in:

```text
reports/runtime-bug-report.md
reports/runtime-payload.json
```

You are now manually debugging the exact execution that generated the AI bug
report, not a different rerun.

Use **Continue**, **Step Over**, **Step Into**, **Step Out**, **Call Stack**,
**Scopes**, and **Locals** as with a normal VS Code Python debugging session.

## Run A New Incident

To generate a new live batch, recording, and report:

1. Stop the current VS Code debugging session.
2. Return to a host terminal in the repository.
3. Run:

   ```bash
   make run
   ```

The generated artifacts from the previous run are replaced. The new batch,
order, and customer values should differ, while replay and the AI report must
preserve the new values exactly. Do not run `make clean` before opening the new
recording in VS Code.

Remove live-demo containers, volumes, and generated artifacts:

```bash
make clean
```

Remove the standalone debugger verification container:

```bash
make debugger-clean
```
